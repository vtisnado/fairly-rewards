# UI: Screens (draft)

All screens are mobile-first, English, and show a visible top banner. Regular pages show "NEAR testnet · test money only"; screens that act as the shared demo account (demo business dashboard, demo counter) show a violet banner "Demo account · sample data · test money". The demo dashboard overview also shows a "Sample data" label.

## Merchant (`/business/<slug>`)
- **UI-001** Setup at `/business/new` in five steps (Brand, Rewards, Boosts, Locations, Fund): name, web address (slug, checked for availability), type of business (MCC), brand color presets or custom, optional logo link, cashback %, tiers with perks, royalty %, expiry, daily cap per location, boosts, locations picked on a map, and test money for the pool. Live preview of the pass card. After launch, the owner edits name, color, logo, cashback and perks from the same form; the other terms stay fixed.
- **UI-002** Dashboard per program: member sales over 7, 30 or 90 days, cashback given, royalties earned, pool balance with runway and a fund button (faucet shortcut in the demo), passes issued, cashback today vs. cap, returning-customer share, live recent events. Cashback and royalty show an info button that explains each term. Periods can be a custom date range from a calendar and compared with the previous period. The sidebar collapses to icons with tooltips. Tables are paginated. A customer row and a device row open a side panel with details and paginated history. The demo program can add locations.
- **UI-003** Counter devices and managers connect with a pairing code: the device (`/cashier/<slug>`) or manager (`/business/<slug>/team`) creates its own key, registers its public account id and shows a 6-character code valid for 15 minutes; the owner (or a manager, for devices at their location) types the code to add it on chain. Private keys never leave the device and never travel in links. Devices can be paused and reactivated.
- **UI-004** Print/display the join QR code for `/join/<slug>`.
- **UI-005** Setup step "Fund" offers first deposits of $20, $50 and $100 plus a custom amount (minimum $20, maximum $1,000) and shows the "Start small" explanation (PROG-019).
- **UI-006** The dashboard overview shows "Pending to settle" (the program's `pending_total`) with the number of cards waiting and a "Settle now" button that deposits exactly that total through the existing funding flow (faucet then `ft_transfer_call` with `{"fund": slug}`; the shared demo does it on the server from the on-chain total). When the oldest pending purchase of a card still pending is 7 days old or more, the panel turns red with "Weekly settlement overdue". The funds screen shows the same pending total with a Settle now action and the "Start small" note (RUN-008, RUN-009).

## Cashier (`/cashier/<slug>`)
- **UI-010** *(a customer code is the primary way to identify a customer, see WAL-007..010)* Identify the customer by scanning a QR with the camera (native `BarcodeDetector` when available), by typing the card code (`W8W-CYA`), or, on the demo program, by picking one of the cards issued in the last hour. A customer account QR without a card issues the card first (PASS-002).
- **UI-011** Numeric keypad for the amount (cents, max 1,000.00), live cashback preview with the effective rate, optional category chips (Coffee, Food, Bakery, Retail, Other), confirm, then a success screen with cashback added and tier-up when it happens.
- **UI-012** "Balance code" mode: type the code shown on the customer's phone (`W8WCYA-3`). The screen MUST show amount or perk and MUST mark the code as honored so it cannot be honored twice. A live list shows codes waiting at the counter.
- **UI-013** Layout follows the prototype: two columns on tablets (card left, keypad right), stacked on phones. The header shows the location and cashback issued today against the daily cap, updated in real time.
- **UI-014** A paired device signs `issue_pass` and `record_purchase` with its own key through the relay, and proves its key to the server when it honors a balance code. The shared demo program also works without pairing, signed on the server with the demo cashier key.
- **UI-015** After a customer is resolved, the counter shows Available (redeemable) and Pending next to visits and level (WAL-022).

## Customer (`/join/<slug>`, `/pass/<token_id>`)
- **UI-020** *(amended by WAL-002: the join adds the card and opens the wallet)* Join screen: one button "Get my card" → onboarding (ONB) → QR to show the cashier.
- **UI-021** Pass screen: card artwork, balance in USD, tier, progress to next tier, perks, expiry warning, pass QR.
- **UI-022** Actions: redeem (amount), claim perk, list for sale, cancel listing, export key.
- **UI-023** Link to the pass in a NEAR explorer.

## Market (`/market`)
- **UI-030** List of passes for sale: artwork, program, tier, value inside, price, buy button.

## Art (`/api/art/<slug>/<tier>.svg`)
- **UI-040** Returns an SVG card using program colors and tier styling (Bronze/Silver/Gold visual differences). Cacheable.

## Landing (`/`)
- **UI-050** One-screen explanation for judges: problem, 3-step flow, "Try the 5-minute demo" and "Start your business" buttons; the demo steps live on `/demo` (demo banner "Demo café · sample data · test money"), real use on `/business/new`.

## Home screen shortcuts
- **UI-060** *(card manifest superseded by UI-067; counter, dashboard and market manifests unchanged)* Each context has its own web app manifest with the Fairly icon (192, 512 and a maskable 512): the customer card (`/manifest/card/<slug>.webmanifest`, name `<Business> · Fairly`, short name the business name cut to 12 characters, start at `/join/<slug>`), the counter (`/manifest/counter/<slug>.webmanifest`, name `<Business> Counter`, start at `/cashier/<slug>`), the dashboard (`/manifest/dashboard/<slug>.webmanifest`, name `<Business> Dashboard`, start at `/business/<slug>`) and the market (`/manifest/market.webmanifest`, name `Fairly Market`). The slug is validated and a program that does not exist answers 404. Display is standalone.
- **UI-061** Each page links its own manifest and sets the Apple web app title, capable and status bar meta tags. The manifest endpoints are served with the manifest media type and are not indexed.
- **UI-062** *("customer card" context is now the wallet, see UI-067)* Install offer by platform: Chromium with `beforeinstallprompt` shows an "Add to home screen" button that opens the native prompt; iPhone and iPad Safari show a bottom sheet with the three steps (Share, Add to Home Screen, Add); other iOS browsers say to open the page in Safari; desktop and Android without the event show nothing; an app already running standalone never shows the offer.
- **UI-063** *(the customer offer appears on the wallet home, see UI-067)* The offer appears once at a sensible moment and "Later" is remembered per context and business: on the customer card after the protect step is settled, on the counter once the device is connected, on the dashboard after it loads. Every app also keeps a permanent entry to open it again: the customer help sheet, the counter header, the dashboard settings and the market header.
- **UI-064** *(for the customer the shortcut is the wallet and connects once, see WAL-014)* A home screen app on iPhone has storage apart from Safari, so it does not find the card or business key. A card or dashboard opened standalone without a key MUST show "Connect this shortcut": it creates a fresh key, shows a 6-character code valid for 15 minutes and opens by itself once connected. The same screen offers the backup file, email recovery and "I don't have a card yet" (card) or view-only access (dashboard). The counter keeps its device pairing screen.
- **UI-065** *(the customer connects the wallet once, see WAL-014)* In Safari, the customer help sheet and the dashboard settings have "Connect home screen app": the user types the code, the app adds the new key to their account with a full-access key (sender equals receiver) and marks the code as connected. The shortcut trusts the connection only after the key is found on that account on chain. The iOS install sheet tells the user the shortcut is connected once with a code.
- **UI-066** *(superseded by NFR-015)* No service worker is registered and nothing from the API or the RPC is cached by the shortcuts.
- **UI-067** The customer context has one manifest, `/manifest/wallet.webmanifest`, name `Fairly`, short name `Fairly`, start at `/wallet`, standalone, with the Fairly icon set. It replaces the per-card manifest `/manifest/card/<slug>.webmanifest`, which answers 404. Counter and dashboard manifests stay per business.
- **UI-068** The wallet page `/wallet` links the wallet manifest, shows the install offer once (UI-062 rules, remembered as context `wallet`), and keeps a permanent "Add Fairly to home screen" entry in its help sheet.
- **UI-069** The wallet screens follow `design/wallet.html`: home with the "Show my code" action and the stack of cards, the code screen, the card detail, the empty state after a first join, and the counter screens after a code is resolved.
- **UI-070** Card detail at `/wallet/<slug>` reuses the pass screen (UI-021, UI-022): balance, stamps, tier progress, perks, history, redeem, sell on the market, backup and explorer link. Back returns to the wallet.
- **UI-071** The card detail shows Available and Pending as two tiles, the pending note, and a disabled "Sell this card" with an explanation while pending is above 0 (WAL-021, SALE-012). The wallet stack chip adds the pending amount.
