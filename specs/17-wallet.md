# WAL: Customer wallet and rotating code (implemented)

One customer app holds every card. Each card stays a separate NEP-171 NFT per business with its own balance, stamps and tier (PASS-*), and all of them belong to the one account behind `fairly.customer.key` (ONB-016). Decision: D-043.

## Requirements
- **WAL-001** `/wallet` lists every card owned by the customer account (`nft_tokens_for_owner`), newest activity first, each with card art, business name, balance, tier and stamps toward the next tier. Cards update live from events (EVT-004, ONB-009). Total balance across cards is shown at the top.
- **WAL-002** `/join/<slug>` stays as the entry from the business QR. It creates the account if there is none (ONB-001, ONB-016), gets the card for that program (ONB-008 for the demo program; for other programs the cashier issues it, see WAL-010) and then opens `/wallet` with that card highlighted. A customer who already holds a card of that program goes straight to the wallet.
- **WAL-003** A customer with no cards sees an empty state with a short explanation, a hint to scan a business QR, and a link to the market. After the first card is added from `/join`, the wallet shows that card with a welcome message once.
- **WAL-004** The wallet home has "Show my code" as the highlighted center button of the bottom navigation (raised coral circle with a QR icon), always visible and above the scrolling content. The card list scrolls under the bar with enough bottom padding for the last card to clear it.
- **WAL-005** The code screen shows one large QR fitted inside its frame with padding and rounded corners and, below it, the typed fallback code in the form `XXX-XXX`. It shows a countdown ring until rotation and a hint to raise the screen brightness, and keeps the screen awake where the browser allows. It never shows a card or a balance and has no connection indicator.
- **WAL-006** Rotation: the wallet requests a new code before the current one ends, so there is always a valid code on screen. A code lives 3 minutes. When a new code is issued the previous one stops working. A code is consumed when a counter resolves it (WAL-018), and the wallet requests a fresh one when its screen is opened and when the account has new activity. If the wallet is offline, the screen says so and shows the last code until it expires, then a refresh button.
- **WAL-007** `POST /api/customer-code` issues a code pair. The body carries the customer account id, public key, signed time and an Ed25519 signature over `fairly-code:<accountId>:<signedAt>`. The server MUST accept it only when the key maps to the implicit account id, the signature verifies and `signedAt` is within 5 minutes, using the same checks as `lib/server/device-proof.ts`. It generates a QR token (WAL-016) and a typed code (WAL-017), stores `(token_hash, code, account_id, expires_at, used_at)` in `customer_codes` (Supabase, server access only), deletes earlier unused rows of that account, and returns token, code and expiry. It is rate limited per IP and per account.
- **WAL-008** The QR payload is `fairly:c:<TOKEN>` where TOKEN is the long random token of WAL-016. It is not a URL and does not contain the account id. The typed code is accepted with or without the dash and in any case, with Crockford decoding.
- **WAL-009** `POST /api/cashier/customer-code` resolves a token or a typed code for a program. The counter sends the slug, the token or code and its device proof (cashier key signature, `verifiedDevice`); the demo program also works without pairing (UI-014). The server MUST refuse unknown, expired or already consumed values with `CODE_NOT_FOUND`, devices that are not cashiers of the program with `NOT_CASHIER`, and rate limit resolve attempts per counter device (and per IP for unpaired demo use), with a stricter limit on failures. On success it consumes the code (WAL-018) and returns the customer account id and, if that account owns a card of the program, the card (token id, balance, visits, tier). The response never lists cards of other businesses.
- **WAL-010** On a successful resolve the counter continues the existing flow for that card with no extra step (UI-011 purchase, UI-012 balance code, redeem and perks). If the customer has no card of this program, the counter shows "No card yet" with a button "Issue card" which calls `issue_pass(slug, owner)` signed by the device (PASS-002) and then continues with the new card. For a first-time customer the purchase and the card creation happen in one confirmation, as for a new customer today.
- **WAL-011** Typed fallback: the counter has a field that takes the 6 characters, formatting as `XXX-XXX` while typing, with the same result as a scan. The existing card code (`W8W-CYA`, PASS-004) remains accepted as a second way to identify a card (UI-010) for customers who show a card instead of the wallet.
- **WAL-012** Privacy: codes are random and unrelated to the account (NFR-016, WAL-019). The counter learns the customer account id only for its own program; ownership of cards is public on chain, so this is not a new disclosure, but the app never shows the counter other businesses' cards. Rows in `customer_codes` are deleted after expiry.
- **WAL-013** Card detail `/wallet/<slug>` and the sell action are described in UI-070 and SALE-011. Backup and recovery (NFR-013, ONB-013) are account level and are reached from the wallet help sheet as well as from each card.
- **WAL-014** Home screen: the wallet is the one customer shortcut "Fairly" (UI-067). On iPhone it is connected once with a code (ONB-017). Counter and dashboard shortcuts stay per business (UI-060).
- **WAL-015** (future) Apple Wallet and Google Wallet passes for a card MAY be offered later. Not part of this scope (TASKS backlog).
- **WAL-016** The QR carries a random token of at least 128 bits from a cryptographically secure source, encoded base64url (22 characters or more). At that size collisions are not a practical concern, so no uniqueness check is needed beyond the unique constraint. Only a hash of the token is stored.
- **WAL-017** The typed code is a fallback for a screen the camera cannot read. It has 6 characters from an unambiguous alphabet without `0`, `O`, `1`, `I` and `L` (Crockford Base32 subset), shown as `XXX-XXX`, following the user code guidance of RFC 8628 section 6.1 (short, case-insensitive, no look-alike characters, limited lifetime, attempts limited). It MUST be unique among active codes: Supabase has a partial unique index on `code` where `used_at is null` (an index predicate cannot use `now()`, so expired rows are deleted before every insert and lookups also filter on `expires_at`), and the insert retries with a new code on a conflict. Because the code space is small, the rate limits in WAL-009 are what protect it.
- **WAL-018** A code pair is single-use per sale: resolving it by token or by typed code consumes both. A customer who needs a second action in the same visit shows the wallet again, which already holds a newly rotated code (WAL-006). The pair expires 3 minutes after issue whether used or not. This follows the dynamic QR pattern of EMVCo merchant-presented and consumer-presented payment codes: short-lived, generated per transaction, validated server side.
- **WAL-019** Codes live in their own namespace. Neither the token nor the typed code is derived from, or comparable to, an account id, a card id or a card code (PASS-004). A typed code that looks like a card code is looked up as a customer code only, and the two are told apart by the counter field the cashier uses (WAL-011).
- **WAL-020** The wallet card list has a sort selector: Recent, Nearest, Highest balance and Oldest. The list is a stack in the style of a physical wallet: cards overlap vertically, each shows its top strip (logo, business name, balance chip) and the last card is fully visible. Tapping a card opens its detail (UI-070).
- **WAL-021** The card detail MUST show Available (`balance`) and Pending (`pending`) as separate amounts. When pending is above 0 it shows "Pending · confirms when the shop settles". Use balance and balance codes use Available only. The wallet stack chip shows the available balance plus "+<amount> pending" when pending is above 0. Selling follows SALE-012.
- **WAL-022** When the counter resolves a customer (customer code or card code), it shows the card's Available (redeemable) and Pending amounts. After a purchase whose cashback exceeds the pool, the confirmation says how much is pending until the shop settles.

## Acceptance
- Given Maria holds cards from Corner Café and Crumb Bakery, when she opens `/wallet`, then both cards show with their own balance and tier, and "Show my code" is visible.
- Given Maria is on the code screen, when 3 minutes pass, then the QR and the typed code have changed, and the old typed code entered at the counter answers `CODE_NOT_FOUND`.
- Given a code was resolved by a counter, when another counter (or the same one) resolves the same code or token again, then the answer is `CODE_NOT_FOUND`.
- Given two active codes are generated at the same moment, then their typed codes differ, and an insert that hits the unique index is retried with a new code.
- Given a counter device sends more resolve attempts than its limit within the window, then it receives `RATE_LIMITED`.
- Given the Corner Café counter scans Maria's code, when she has a Corner Café card, then the counter shows that card and its keypad, and no Crumb Bakery data.
- Given the Crumb Bakery counter types Maria's code and she has no Crumb Bakery card, when the cashier taps "Issue card", then a pass is minted to Maria and the purchase flow continues with it.
- Given a device that is not a cashier of the program, when it resolves a valid code, then the answer is `NOT_CASHIER`.
- Given Maria sells her Corner Café card on the market, then her Crumb Bakery card is still in the wallet and the royalty goes to Corner Café.
